# 当前架构与确认事项

本文件汇总当前讨论，供用户评审；不构成新的批准记录。仅设计，尚未进入实现。

最新进展：P7 的核心会话语义已确认，见 [临时协作会话](collaboration-sessions.md)；P6 的逐对白名单因用户希望全通而重新评估；P9 的全 Agent 串行/默认排队被会话并发和用户 steer 方向替代，具体引擎语义待定。P11 已增加参考旧项目的 [cron 设计](cron-design.md)。下表相应旧候选不作为已确认决定。

## 已确认与当前偏好

- Bot + Agent 共同定义完整的功能和权限，Bot 需提供部分信息。
- 一个 Bot 管理多个 Agent 实例，每个实例固定属于一个 Bot。
- 可以配置新建 AgentTemplate，跨 Bot 复用模板，实例与运行状态独立。
- Agent 之间需要通讯，首版包括经显式授权的跨 Bot 通讯。
- Agent 使用所属 Bot 的身份执行，收到协作请求不改变该身份。
- 用户倾向 Agent 自己管理 Conversation Context、Bot 信息渐进披露；具体会话粒度和身份来源职责仍待确认。

## 当前建议结构

```text
聊天平台 → 渠道适配器 → Bot（入口策略、信息提供器）
                            ↓
                 身份 / 权限 / 路由 / 调度
                            ↓
                 固定属于该 Bot 的 Agent
                 ├─ 模板版本与实例配置
                 ├─ Conversation / Task / Run
                 └─ 引擎适配器与受控工具
                            ↕
              持久化邮箱 → 经授权的其他 Agent

执行结果 → 持久化投递队列 → 原 Bot / 原聊天
```

模板不携带会话、凭据或实际授权。Agent Runtime 管会话历史、摘要和引擎续接；Bot Context Provider 按需提供项目、平台能力等信息；运行时独立持有可信身份、权限和真实回复目标。

身份建议：平台提供发送者事实，适配器验证来源，Identity 模块解析系统身份，Policy 判定操作权限。模型仅获得任务所需信息。Agent 执行外部 API 使用所属 Bot 身份；Bot 不支持的用户身份 API 不自动借用个人账号。

通讯建议：持久化异步请求/回信，执行方使用自己的 Bot 身份。每条授权有方向、有服务与资源范围；结果回传范围随请求固定并在发送前复核。默认结果回请求 Agent 汇总，不能默认自动继承原用户全部权限或读写另一会话。

## 优先确认的产品边界

以下全部为建议，不应仅因写入文档而视为批准。

| 编号 | 待确认事项 | 建议 |
| --- | --- | --- |
| P1 | 项目与旧系统关系 | 独立新项目，参考旧系统经验；首版不迁移生产数据 |
| P2 | 首批平台与引擎 | 首版微信 + 飞书，先接一种 Agent 引擎；建议优先现有 Codex 后端经验，具体接口另核实 |
| P3 | 使用者与管理员 | 先服务个人/受信任小团队；部署管理员管理 Bot，Bot 管理员管理自己的 Agent 和授权，不做公开多租户 |
| P4 | 会话上下文粒度 | 私聊按 Bot+Agent+用户；群聊按 Bot+Agent+群+话题共享，无话题时按群；群聊历史不混入私聊 |
| P5 | 任务访问与控制 | 任务结果继承入口可见范围；取消/重试限发起者及授权管理员，群成员不自动获得控制权 |
| P6 | 全通范围（重新评估） | 用户希望全通；信任范围、执行和结果权限待定 |
| P7 | 协作会话（核心已确认） | 首次仅继承配置，多轮复用自己的上下文，固定配置版本，空闲回收；TTL 待定 |
| P8 | 模板与 Agent 管理入口 | YAML + 管理命令创建/注册模板；聊天命令选择模板创建实例，首版不通过聊天自由编写模板、不自动升级既有实例 |
| P9 | 并发与输入 | 同会话串行、不同协作可并行；用户希望直接 steer，具体引擎规则待定 |
| P10 | 工作区与权限边界 | 每实例显式绑定工作区；同项目并行编辑优先用 worktree；实际 OS 隔离等级按信任模型选择 |
| P11 | 首版附加功能 | cron 已确认独立上下文、固定配置、不重叠并跳过；其他参数、首版范围与其他附加功能待确认 |
| P12 | Bot 身份能力不足时 | 明确返回不支持，不回退到个人身份；是否另设授权服务账号能力应单独决定 |

P4 的群聊共享意味着进入该群会话的参与者可以接触该会话模型已看到的内容；新增/退出成员及私人资料输入的规则必须明确。成员变化涉及敏感历史时应考虑新建 Session，而不能仅靠权限变更令模型忘记旧信息。

P6 的定向调用建议正在重新评估；同一协作的回信和追问仍需关联正确来源与会话。对方问题需要用户决定时，经原请求 Agent 回到用户，等待期间不占执行槽。

协作展示建议：用户看到受允许披露的协作对象、任务摘要、进度和最终汇总，完整内部消息按权限查询，不逐条刷屏。规则范围内的协作自动执行，不要求每次重复确认；该展示和交互方案尚待确认。

## 技术细节建议由设计阶段继续给出默认值

已确认 Rust、Codex、个人使用、最多 20 Worker。建议单机、模块化控制平面、SQLite WAL 与文件系统附件；操作系统、物理 Worker 布局和恢复参数待定。

需要在实现前补齐但无需用户逐个设计：接口 schema、引擎/渠道兼容矩阵、租约与心跳时长、取消/重试策略、资源配额、模板 schema 校验和错误码。保留期、备份目标、停机接受程度和费用预算具有产品影响，应另提供明确默认值供确认。

执行状态与投递状态分开；有未知外部副作用的任务不盲目重跑；平台没有幂等发送能力时不承诺绝对无重复投递。

## 确认顺序

建议先确定 P1–P4，再确定 P5–P12。随后给出具体接口、配置示例、容量与恢复参数，形成最终架构版本供确认；最终架构确认与开始实现授权仍需明确。
