# Bot 与 Agent 的组合契约

状态：用户已确认组合原则；以下对象拆分、字段和执行规则为建议细化，待讨论。本文件不构成实现授权。

最新设计偏好：用户倾向 conversation context 由 Agent 自己维护，Bot 信息渐进式披露；已确认 Agent 以所属 Bot 的身份执行；用户身份信息的提供与验证职责尚待讨论。以下第 8 节具体化这一偏好，涉及上下文加载的解释以第 8 节为准。

## 1. 已确认原则

用户明确提出：“bot+agent 定义完整的权限以及功能。有一些信息是需要bot给出”。因此，不能只在 Agent 上定义服务能力，也不能把 Bot 简化为收发消息的通道。

已确认首版采用固定归属：一个 Agent 实例只属于一个 Bot，一个 Bot 可以管理多个 Agent。不同 Bot 可以复用 AgentTemplate，但不共享 Agent 实例。无需独立的多对多 Binding 对象，由 Agent 的固定 bot_id 表达归属。

## 2. 职责划分

| 对象 | 定义或提供的内容 | 边界 |
| --- | --- | --- |
| Channel Adapter | 平台认证事件、收发接口与技术能力 | 不决定业务权限 |
| Bot | 入口身份、接待范围、入口功能与策略、上下文提供器 | 平台权限不等于用户授权 |
| AgentTemplate | 可复用的角色、技能、引擎默认配置、能力需求 | 不包含会话、任务、凭据或实际授权 |
| Agent 实例 | 固定 bot_id、模板版本快照、工作区、实例策略、会话与任务 | 不可经另一 Bot 接管或改写归属 |
| Policy / Context 服务 | 联合授权判定、来源验证、按需信息查询 | 不把普通内容升级为身份或授权 |

模板配置与实例化规则见 [Agent 模板设计](agent-templates.md)。创建另一 Bot 下的 Agent 会产生全新的实例及状态；共享模板不意味着共享记忆、执行队列或工作区。

## 3. 功能如何组合

服务功能来自 Bot 自有功能（帮助、路由、状态查询等）及实例配置开放的 Agent 功能（分析、编码等）。即使是 Bot 自有功能也需检查操作权限。

每项功能声明：function_id、由谁执行、所需权限、所需渠道/引擎能力、所需上下文字段、输入输出类型，以及缺少能力时是否允许降级。

Agent 功能只有在 Bot 愿意提供、实例配置已开放、Agent 能执行且所需上下文齐备时才可用。功能组合不能简单视为两个列表求并集；某个 Agent 不需要发消息权限的纯计算任务，也不应被要求具备无关的平台权限。

## 4. 权限如何组合

针对每次操作，联合判定：用户对该 Bot/Agent/资源的授权、Bot 的入口策略、Agent 的工具与资源策略、实例策略限制、Task 能力范围，以及实时撤权状态。涉及平台操作时，再检查渠道账号的实际 scope 与资源可见性；本地文件操作则检查工作区与系统隔离规则。

建议将同一操作的约束归一后取共同允许范围：任何适用限制拒绝，都拒绝；未声明的权限默认不授予。角色名称或不同平台 scope 不直接做字符串集合求交。已有任务的能力快照是上界，后续撤权可以继续收窄，新授权不能自动扩大正在运行的任务。

例：同一开发模板创建两个独立实例：审查 Bot 下的实例只开放代码审查，开发 Bot 下的实例在授权后允许修改；两者的会话与任务分别管理。

工具网关校验服务端产生的 bot_id、agent_id、principal_id、task_id 与目标资源。Worker 不能靠在请求中更换 bot_id 来借用另一 Bot 的权限。平台身份由具体连接及凭据引用确定。

## 5. 哪些信息需要 Bot 提供

以下是建议候选，并非用户已经确认的完整字段清单。Bot 可委托平台适配器、身份服务或上下文提供器读取；由服务端核验后提供给 Agent。

| 信息 | 典型内容 | 处理方式 |
| --- | --- | --- |
| 入口身份 | bot_id、平台、租户、渠道账号 | 从真实接入连接解析，不信任消息正文 |
| 请求者与会话 | principal、chat/topic、私聊或群聊、经过验证的成员角色 | 带来源与校验时间，敏感动作重新核验 |
| 回复条件 | 原始回复目标、引用关系、文本与附件限制、编辑能力 | 真实目标由投递层持有；Agent 只取得所需描述或受限引用 |
| 服务能力 | 实例配置开放的功能、可用工具、资源范围和限制 | 作为执行能力依据，并由工具网关实际强制 |
| 服务配置 | 默认项目、语言、时区、入口业务说明 | 区分管理员配置与用户可编辑偏好；时区不提升权限 |
| 业务上下文 | 当前群绑定的项目、知识库引用、经过授权的业务数据 | 按需读取，限制资源范围与缓存寿命，不默认搬运全部历史 |
| 附件与凭据引用 | 授权后的附件引用、可调用外部服务的句柄 | 不把渠道密钥或长期令牌放入提示词 |

Agent 为功能声明 required_context / optional_context。BotContext 标注 schema_version、source、verified_at、expires_at、sensitivity 与字段值；实际是否持久化值或仅保存引用由数据敏感性确定。字段按使用阶段加载，而非任务开始前全部注入；具体动作缺少必需字段时暂停该动作，其他已具备条件的工作可以继续。不能让模型猜测身份、权限或默认回复地址。

可信来源不等于内容可信：从平台正规接口读取的群消息、文档正文仍是外部内容，不能覆盖程序策略、管理员配置或提升权限。功能权限与这些内容分开传递，不能只用一段系统提示词承载。

## 6. 一次任务的组装流程

1. 适配器验证事件，服务端定位 Bot 与真实请求者。
2. 路由选择固定归属于该 Bot 的 Agent 实例与功能。
3. Policy 检查访问权，Context 服务提供最小入口摘要和可查询的信息目录；具体 Bot 信息按动作需要加载。
4. 校验本阶段必需上下文，保存 Bot、Agent 实例及模板快照版本和任务能力快照。
5. 构造运行时私有 ExecutionContext，包含可信身份、有效能力与真实回复目标；模型输入另行投影，只包含任务输入、必要摘要、受限附件引用及查询接口。
6. Worker 经引擎适配器执行；工具动作逐次由网关核验有效权限及实时撤权。
7. 结果通过原 Bot 的原始回复目标投递，投递前再次检查必要的可见性和账号状态。

建议 Session 的隔离键包含 agent_id 与 conversation 范围；bot_id 必须与 Agent 固定归属一致。群聊是否再按请求者隔离待确认。不同实例不合并私有历史或复用入口凭据。

跨 Agent 委派保留原始 Bot、请求者与任务来源，只传递必要的上下文和缩小后的能力；目标 Agent 必须另有有效委派授权。Agent 间通讯已列为需求；首版包含经过显式授权的跨 Bot 通讯。接收方始终以自己的 Bot 身份执行，委派授权与结果出口规则见 [通讯设计](agent-communication.md)。后台任务则使用明确授权的服务身份与目标，不伪造当前聊天用户。

## 7. 待确认项与验收约束

需要继续讨论：Bot 必须提供的业务信息具体有哪些；哪些由配置给出、哪些运行时读取；Bot 是否可跨渠道；上下文覆盖优先级；群聊 Session 隔离规则。

后续验收至少覆盖：同一模板创建的两个实例遵守各自 Bot 的权限；Bot 缺少必需信息时不可运行对应功能；伪造 bot_id/角色不生效；同模板的不同实例无私有信息串用；撤权后工具调用被拒绝；跨 Agent 委派不能借用另一 Bot 的权限。

## 8. Conversation Context、渐进披露与身份来源

### 8.1 上下文分为三类，分别维护

| 类型 | 维护方（建议） | 内容与生命周期 |
| --- | --- | --- |
| Conversation Context | Agent 的 Runtime / Session Manager | 消息历史、工具结果、会话摘要、引擎 session_ref；负责续接、压缩和新建会话 |
| Bot Context | Bot 的 Context Provider | 渠道能力、业务配置、入口绑定资源、可核验的会话属性；按需查询，保留来源和有效期 |
| Execution / Identity Context | 控制平面的 Identity / Policy 与任务运行时 | 本次调用的真实身份、租户、Agent 归属、授权范围与回复目标；每次请求重新绑定并执行实时校验 |

这里“Agent 自己维护”是 Agent 侧程序负责持久化与生命周期，不是只存在模型窗口里。共享存储模块可以负责物理写入，语义所有权仍在 Agent 会话管理层；引擎有原生会话续接能力时由 Engine Adapter 使用，不强制复制其内部隐藏状态。Bot 保留用于收发、去重和审计的消息记录，但不另行维护或拼接一套模型对话历史。

同一个 Agent 可拥有多个独立 Conversation。Agent 拥有上下文，不代表它的所有用户、群聊、Bot 共享一份上下文。沿用默认 Bot/Agent/会话隔离，群聊共享上下文与个人子会话的具体规则待确认。首版不支持跨 Bot 接续；同 Bot 内切换 Agent 的会话行为和长期记忆共享必须另行定义，不能由相同 principal 自动推断。

### 8.2 渐进式披露

初次给模型的内容只需当前消息、最小的入口摘要（例如群聊/私聊、语言）和可查询能力目录；用户输入与可信运行时元数据分开传递。实际权限、身份及回复目标可以从一开始就在运行时完备，但不需要全部展示给模型。

当工作涉及特定信息时，Agent 通过受控 Context API 请求能力信息、项目引用、必要身份资料或渠道输出限制。API 的 Bot、请求者、租户和 Agent 作用域由运行时绑定，调用者不能任意换一个 bot_id 或 principal 查询更高权限数据。查询失败应区分不存在、未授权、过期和服务不可用。

信息返回后可作为工具结果进入 Agent Conversation Context；Agent 可以摘要和记忆其中对任务有用的内容，但历史工具结果不再是当前权限的权威来源。权限、成员关系等动态事实在敏感操作前重新检查；缓存按来源、版本和有效期失效。撤权阻止后续访问，但无法令已经进入模型历史的信息自动消失，涉及敏感信息删除时必须清理相应摘要/历史并按需重建引擎会话。

### 8.3 身份由谁提供

建议采用“平台提供事实、适配器验证来源、Identity 服务解析系统身份、运行时绑定授权主体、Agent 按需获得资料”的职责链。Identity 服务是控制平面的逻辑模块，首版无需独立部署。

| 身份问题 | 权威来源与处理方 |
| --- | --- |
| 消息来自哪个平台账号、租户、群或用户 | 平台的认证事件，经 Channel Adapter 校验来源、账号和事件字段 |
| 当前由哪个 Bot 接待 | 受验证的渠道连接与服务端 Bot 注册配置，不取正文中的声明 |
| 平台用户对应系统哪个人 | Identity 服务查询受验证的 identity_binding，得到 canonical principal；未绑定者仅在本平台范围内识别 |
| 名字、部门、群角色等资料 | Bot 的 Context Provider 按权限读取平台目录/成员 API；显示名仅作展示，不作唯一身份 |
| 当前运行的是哪个 Agent、代表谁执行 | Supervisor 与 Policy 根据 Agent 固定归属与 Task 来源生成，不能由 Agent 在调用参数中自行声明 |
| 可以执行哪些动作 | Policy 联合用户、Bot、Agent 实例与资源规则判定，不从自然语言身份说明推导 |

Agent 不负责证明用户身份，也不需要每次拿到真实姓名和平台原始 ID。它可先使用“当前请求者”这样的逻辑引用；只有任务确实需要姓名、组织等信息时才查询。无身份绑定时是否允许受限访客、是否要求注册及跨平台绑定证明方式，仍待确认。

任务分别记录 requester（谁提出）、executor（哪个 Agent 执行）、credential_subject（外部 API 使用所属 Bot 对应的执行身份）与 audience（谁能看到结果）。这几者可能不同，不能因为 Bot 有平台权限就推断请求者有同等权限。

身份事实缺失时按访问策略拒绝或使用明确受限访客身份，不让模型根据昵称、对话自称补全；平台不支持验证的属性必须标为未知。协作任务传递原请求者的可信来源与收窄后的授权，外部发言正文不能替代该来源链。

### 8.4 需要补充的验收场景

Agent 续接会话无需 Bot 重放完整历史；未涉及 Bot 详情的任务不加载无关资料；Context 查询不能越过 Agent 的 Bot 归属窃取信息；旧历史中的管理员身份在撤权后不再授权；同一 Agent 的多个会话互不泄露；身份查询和外部 API 的实际凭据主体可分别审计。
