# 飞书流式卡片超时恢复规划

状态：超时恢复已实现，真实超过 10 分钟的飞书验收尚未进行。只改变飞书投递状态机，保留共用回复收集、任务状态和普通消息兜底。

已实现结构化错误码、send/content/open/close 持久化操作类型、旧 pending 兼容、最高分配序号记录、200850/300309 受限恢复及取消/代次切换/off 禁止续开。网络结果未知时复用原操作；连续失败保留已有兜底。取消时关闭卡片，状态通知走普通消息，不为了补写取消文字重新开启。

修正 CLI 输出通道：lark-cli 的失败 JSON 在 stderr，成功结果在 stdout。卡片适配器同时读取两者，仅解析结构化错误码，不记录原始 stderr。回归 mock 按真实 CLI 将失败写入 stderr，并覆盖 stdout 兼容、非 JSON 错误及敏感内容不泄露。先前只解析 stdout 会把超时错误误判为 invalid card response，导致无法进入重新开启分支。

## 已确认与未确认

- 官方流式更新说明：距上次开启 10 分钟后自动关闭。
- 文本更新错误码 200850（流式超时）、300309（流式已关闭）明确指示通过 settings 接口将 streaming_mode 设为 true。支持同一卡片恢复，无须新建消息。
- settings 与 content 都要求递增 sequence，支持操作级 uuid。
- 文档未明确保证已开启时再次设置 true 会刷新计时；不能未经实测把定时 true 当作可靠续期方案。

## 实施步骤

1. 将飞书接口错误改为结构化类型，保留错误码、操作类别和可用的请求追踪 ID；不保存凭据、正文或原始响应。区分明确拒绝和响应未知。
2. 将持久化操作从 close 布尔值扩展为 send/content/open/close 类型，兼容既有 pending 数据。持久化最高已分配序号，不能仅依赖最后成功序号。每项操作有固定 UUID、序号及不可变请求内容。
3. 活跃任务的 content 收到 200850/300309 时，原子保存恢复转换：保留目标文本、废止已明确拒绝的内容操作，分配更大的序号执行 open；成功后以更大的序号及新 UUID 提交当前最新全量文本。保留 card_id 和 message_id。
4. 网络超时或响应未知时，不推断卡片关闭；重试相同操作/序号/UUID。不能为同一 UUID 改请求内容，不能在 open 后重用更小的旧 content 序号。
5. 每次更新最多一次 open 后重试，恢复连续失败再走已有有限重试及未送达后缀兜底。已送达内容不因恢复而重发普通消息。
6. 每次网络操作前复查任务代次、终止状态和配置开关。取消、失败、旧代次和 off 不再续开，只尽力收尾。成功结束时如还有未送达最终文本，可进行一次受限恢复、写入、关闭；关闭接口报告已关闭时，仅在全文已确认送达的条件下视为展示已完成。
7. 不自动恢复所有旧 failed 卡片，不重放已完成任务。历史恢复另行显式指定，避免补发旧消息。

## 验证

本地模拟覆盖 200850/300309→open→content→close，序号严格递增，重复错误有上限，open 前后崩溃恢复、响应未知重试、取消/代次切换/off、最终内容去重及旧数据兼容。

真实验收需指定测试会话：
- 开启测试卡片，等待超过 10 分钟，确认文本更新返回超时/关闭错误；重新开启原卡片后更新成功，消息 ID 不变，再关闭。
- 如需提前续期：开启后第 8 分钟再次设置 true，在原始开启第 11 分钟更新；另设未续开的对照卡片。该实验只能验证观察到的行为，文档未保证时仍保留错误恢复。
- 使用可控时间的模拟测试验证时序，不能用其替代真实 10 分钟平台行为。

先实现明确支持的恢复机制，真实验收后再决定是否增加提前续期。上线保持按 Bot 开关，先 Kick；不改微信流程，不改聊天 profile。
