# 定时任务设计（参考 codex-on-wechat）

状态：用户已接受三项核心建议：每次触发独立上下文、Job 固定配置版本、同 Job 未完成时跳过重叠触发。其余细节、参数与首版范围待确认；不创建任何真实计划，不构成实现授权。

## 1. 参考依据与适用边界

已读取旧项目 architecture.md 的 Durable cron scheduling 段、src/runtime/cron_schedule.py、test_cron_store.py 和 test_cron_ephemeral_worker.py 的相关案例。旧文档 schema 编号跨章节有漂移，因此以具体代码和测试行为为参考，不据文档断言当前整体数据库版本。

可复用契约：at/every/五字段 cron + IANA 时区；自然语言草案后续输入确认；创建时冻结执行及来源配置；调度事务原子写 Task、firing 和 next_fire_at；唯一 (job_id, scheduled_for) 防重复触发；结果发回原 Bot/chat/topic。旧代码计划数学支持停机后至多一次补跑、跳过中间错过时刻。旧测试表明临时执行器每次新建 clone、不沿用主会话引擎 thread。

新项目将其映射到 Bot、Agent config_revision 与临时执行会话，避免拷贝旧项目全部身份与配置结构。

## 2. 领域关系

Bot → Agent → CronJob → JobOccurrence → Task / Run / ExecutionSession。

CronJob 保存稳定 job_id、创建者 principal、固定 bot_id 和 agent_id（含代次）、schedule/timezone、任务 prompt、冻结的 Agent 配置快照、workspace 引用、能力授权范围、原回复目标、状态、job_revision、next_fire_at 及重叠/补跑策略。Agent 模板只提供初始配置，不直接拥有 Job。

JobOccurrence 表示一次计划触发，保存 scheduled_for、实际处理时刻、状态、Task 引用和跳过/失败原因。Job 可以启用、暂停、停用、完成或因依赖失效阻塞；一次任务失败与计划停用分开。

任务 requester 是创建计划时授权的用户或管理服务主体；executor 是目标 Agent，credential_subject 是该 Agent 所属 Bot 的外部身份。每次触发及工具调用重新检查撤权和目标可用性，不从历史配置授予永久权限。

## 3. 创建、修改与管理

建议自然语言创建采用旧项目的两阶段语义：解析 → 保存有限有效期草案 → 显示时间规则/时区/下次触发/任务内容/目标 Agent/配置版本/回复目标 → 后续用户输入确认 → 原子创建 Job。建议草案有效期 15 分钟。这里是产品建议，不是在当前会话发起实际计划。

确认来自同一授权主体和明确草案范围，不能由模型在同一输入内自行确认。重复确认同一草案幂等。多草案同时存在时使用明确 ID，不能猜测确认对象。时间不明确时保留为待澄清，不创建可执行计划。

建议管理入口支持列表、详情、暂停、恢复、修改、删除/停用、查看执行历史、取消某次运行。修改计划或更新配置先给出差异，沿用所选确认策略；变更创建新 job_revision，已产生的 Occurrence 固定旧版本，不被重新解释。CLI/API 的明确结构化创建是否需要同等确认待定。

暂停阻止后续触发，不自动取消在途 Task；取消一次 Task 不删除周期计划。恢复从现在计算下一触发，默认不补暂停期间的工作。删除采用软停用并保留历史，在途任务取消需明确选择。

## 4. 时间语义

建议支持 at（一次）、every（固定间隔）、cron（五字段日历），默认 Asia/Shanghai，但展示时始终写明时区，数据库时间存 UTC。相对一次性请求解析成绝对 at，不误解成周期 every。

every 使用固定时间锚点，执行耗时不改变后续节奏；cron 遵循当地日历。沿用旧实现的 DST 候选规则：不存在的本地分钟跳过，重复分钟只触发一次（精确选择需与解析模块确认并固定验收）。最短间隔、最大计划数及单任务时限待定。

## 5. 执行会话与配置

已确认每次 Occurrence 创建独立临时执行会话，仅加载 Job 固定的配置与任务 prompt，不注入创建计划时的聊天历史，也不复用用户主会话或上一次 cron 的历史。Bot 信息仍按需读取。可持续数据由显式、获授权的项目文件或任务状态存储提供。

已确认 Job 固定创建/明确更新时的 config_revision，Agent 后来改 system prompt 不自动改变旧计划。每次启动若技能/模型/工作区已不可用，标记阻塞或失败并通知，不静默替换引擎或路径。权限撤销实时生效。

同一 Occurrence 的用户追问可在记录保留期内明确关联到该临时会话继续；下一次周期触发始终是新会话。具体回复关联入口和会话保留期待定。任务内部可按正常规则调用其他 Agent，并复用各自 collaboration_id 多轮协作。默认不向 cron 或协作任务授予创建更多计划的能力，避免递归生成长期任务；后续如需开放需另定义授权。

## 6. 到期调度、并发与重叠

调度器只创建普通任务，不直接调用模型。单事务检查 Job 状态/版本/权限，登记 Occurrence，创建 Task/执行请求，并推进 next_fire_at。唯一 (job_id, scheduled_for) 约束与事务避免多调度器、重启或丢失回执造成双触发。重复触发保护不等于外部副作用 exactly-once。

已确认同一 Job 默认不重叠：前次 Task 未终态时，下个计划时刻记为 skipped_overlap 并推进到下一时刻，不无限积压。不同 Job 在总并发限制内并行；用户交互预留容量，计划任务按公平规则调度。等待子任务或用户输入也算该次未完成，不释放 Job 的防重叠占位。

系统容量不足但无同 Job 在途任务时保留一个待执行 occurrence，后续错过时刻不无限生成队列。副作用可能仍在执行的失联 Run 标记 interrupted/needs_attention，在确定旧执行停止前不能解锁成另一次重叠执行。

停机补跑建议沿用旧实现的“最多补一次”：恢复后对错过的周期至多执行一次，其余跳过，下一次跳到现在之后。新项目增加最大迟到宽限作为建议配置，超过宽限不执行陈旧任务而记录 missed；单次 at 过期也明确记录，不悄悄数天后执行。宽限值和是否允许按任务选 skip/coalesce 待确认。

## 7. 结果与失败恢复

成功/失败结果通过 Outbox 返回 Job 固定的 Bot、聊天和话题；不受当前接待 Agent 切换影响，不把任务原始 prompt 作为已完成结果发送。渠道失效保留投递失败记录，不自动转发到其他私聊。投递前复核可见范围，尤其群成员或授权发生变化时。

JobOccurrence 和 Task 关系服务端维护，防止普通文本伪装成定时结果。执行成功与投递成功分开；投递失败只重试发送。无副作用的瞬时执行失败可有限重试同一 Occurrence；外部结果不明时进入需处理状态，不创建另一 Occurrence 盲重跑。

Agent 删除/代次变化、Bot 禁用、授权撤销时阻止新触发并给出可见原因；同名新建 Agent 不接管旧 Job。配置依赖失效通过显式修订修复，Job 不扩大授权。告警频率、连续失败暂停阈值及备份/恢复目标待定。

## 8. 验收与优先确认

验收涵盖：草案不执行、重复确认幂等、同一触发仅一任务、重启去重、停机补跑上限、前次未结束跳过重叠、冻结配置与实时撤权共存、不污染主会话、精确原入口投递、DST、暂停/恢复和取消单次任务语义。

已确认：每次独立会话、Job 固定配置版本、同 Job 不重叠并跳过。停机补跑/迟到上限、自然语言确认与管理流程保留为建议；后续补齐容量、时长、保留期与故障策略供审阅。
