# Agent 通讯与所属 Bot 执行身份

状态：用户已确认需要 Agent 之间通讯，Agent 使用所属 Bot 的身份执行。首版已确认包含经过显式授权的跨 Bot 通讯；以下通讯协议、具体授权配置和路由细节仍为建议。不构成实现授权。

## 1. 身份规则

每个 Agent 固定归属于一个 Bot。内部通讯必须同时识别 agent_id 与其所属 bot_id；调用平台或外部服务时使用所属 Bot 对应的执行身份，身份映射由服务端管理。接收别的 Agent 的请求不会改变归属或执行身份。

建议将身份分为四部分：requester 表示原始请求者，sender 表示当前发出通讯的 Agent/Bot，executor 表示实际执行的 Agent，credential_subject 表示其所属 Bot 对应的外部账号。另记录结果可见范围 audience。不能把这些字段合并成一个 user_id。

身份用来确定“以谁的名义操作”，操作授权还需检查“这个请求允许做什么”。拥有 Bot 身份不等于可以执行该 Bot 技术权限覆盖的全部动作。凭据绑定、请求者权限和 Agent 实例策略均由运行时和网关校验。

本地文件和计算任务没有聊天平台登录身份，仍以所属 Bot 作为逻辑执行主体、Agent 作为执行者进行授权和审计；实际 OS 身份由部署隔离策略决定。外部 API 不支持 Bot 身份时，返回不支持或按另行批准的服务身份映射处理，不能静默改用个人账号。

## 2. 通讯模型

最新已确认的业务语义是非对称 query/response：A 为请求方，B 的临时协作会话为被查询方。B 通常应针对请求回答；A 收到回答后可以使用结果，通过 A 所属 Bot 展示给用户，或在同一 collaboration_id 中提交新的追问。A 不需要再对 B 的回答作答，B 回答后也不因 A 沉默而反复唤醒。B 所属 Bot 只提供 B 的执行身份，不默认直接向用户投递该协作结果。

Mailbox 仅是内部持久化消息存储与投递机制，不是双方对等闲聊规则，也不是 /inbox 用户通知入口。首版可由 SQLite 消息/请求记录和调度器实现，无需外部消息队列服务。对 Agent 暴露 query/结果/续问接口，隐藏底层投递实现。

建议每个 query 有独立 request_id，response 关联该 request_id；整段多轮交流共享 collaboration_id。同一 response 的分片和进度不自动成为新 query。服务端投递/消费确认自动处理，不要求模型额外回复“收到”。B 的正常回答、明确失败/拒绝或需要澄清都应形成可追踪结果，超时或崩溃由运行时反馈，不能假定模型总会成功回答。澄清结果可以由 A 决定继续，不自动形成双方互相等待的循环。

建议将单次请求状态（pending/running/answered/failed/timed_out/cancelled）与协作会话生命周期分开。B 给出回答后，该次请求完成，会话可进入空闲等待可选追问；A 不追问并非失败，也不占用执行 Worker。会话按已定空闲回收机制保留上下文。A 在其他工作中收到 response 时，将其投递到原调用会话并按串行输入规则消费，不同时启动两个写同一上下文的 Run。

建议采用控制平面提供的持久化 Mailbox，不依赖聊天平台群聊转发。Agent 使用受控工具发现可联系对象、发送工作请求或通知、回复结果、查询请求状态。工具名与参数格式待定。普通 Agent 通讯不是对外给人发消息，外部发送需另行授权。

建议支持 request、result、notification 三类消息及结构化取消控制；消息串有 conversation/correlation ID，request 关联接收方任务，result 必须关联原请求。notification 默认只入邮箱，不自动开始新任务，是否唤醒由显式配置控制。投递回执只表示持久化接收，不表示完成。

消息信封包含 message_id、request_id、父请求/父任务、目标 Agent、来源 Agent/Bot、目标 Bot、原请求者引用、消息类型、正文或附件引用、deadline、预算、reply_to、来源链与授权引用。身份、租户、授权引用和 reply_to 由网关根据认证连接与有效 Task 填入或核验；模型只能提供受允许的目标、业务内容和预算请求。

发送先持久化，接收方从邮箱处理；以有效发送方、任务范围和客户端幂等键去重。重复投递不重复创建接收方任务。结果与待发送回信在同一事务中保存，执行事件采用既有 run_id、租约与 fencing 规则。

## 3. 同 Bot 与跨 Bot

用户后续提出 Agent 间全通，原逐对白名单建议正在重新评估；以下定向规则不代表最终决定。全通信任范围与操作/数据权限仍待确定。

同 Bot 下：Agent A 向 B 请求工作，B 使用两者所属的 Bot 身份执行，但仍检查 A 是否有权调用 B、该类工作是否开放及当前任务限制。不能因同属 Bot 而互读所有私有上下文。

跨 Bot 下（首版已确认，需显式授权）：A 属于 Bot X，B 属于 Bot Y。A 的请求经通讯网关送到 B，B 使用 Bot Y 的身份执行并回信；A 继续使用 Bot X 的身份汇总。A 不取得 Y 的凭据，也不将自己的 Bot 身份传给 B 使用。这不要求共享 Agent 实例、合并用户身份或合并会话。

建议通过明确的通讯策略定义：谁可以调用哪个 Agent、允许的工作类型/资源、频率与预算、可传递信息及结果出口。同 Bot 通讯也校验策略；跨 Bot 默认为未开放，需显式配置来源与接收方授权。发现接口只列出调用者可联系对象，不泄露其他私有 Agent 清单。

授权不是简单要求调用者拥有接收方全部底层资源权限。接收方可以显式提供受限服务，例如只提供某项目状态摘要：调用者拥有使用该服务的权限，接收方有执行必要读取的权限，输出按接口合同限制。未声明的操作和资源访问不能通过自然语言请求获得。

接收任务权限来自已批准的委派规则、接收 Bot/Agent 的执行上限，以及父任务允许的委派范围；普通聊天内容不能扩大它。原请求者可以是不在接收平台绑定的外部主体，但来源必须受验证，按已授权的外部调用规则处理，不虚构接收平台用户身份。

### 3.1 显式授权的建议配置边界

授权建议采用有方向的规则：来源 Bot/Agent → 目标 Bot/Agent，并明确允许的服务/动作、资源范围、输出范围、预算及有效期。X→Y 不自动开放 Y→X 的新任务；已批准请求的关联结果可以按其回信范围返回，不构成反向任意调用权限。

规则由拥有相应管理权限的主体配置，跨管理域需满足双方政策。允许发现、允许调用和允许获取结果分别检查；发起执行和返回结果前检查实时撤权。具体规则格式、管理角色及对在途任务的撤权处理仍待确认。

## 4. 上下文、结果与生命周期

最新已确认：首次协作只继承目标 Agent 配置，不复制主会话历史；同一 collaboration_id 多轮复用临时会话自己的最新上下文并固定配置版本，详见 [临时协作会话](../collaboration-sessions.md)。本节旧候选以该确认语义为准。

Agent 维护自己的 Conversation Context；跨 Agent 请求仅提供所需任务描述、授权附件或受限数据引用，不默认携带完整对话。接收方按需读取自己 Bot 的 Context；发送方信息以带来源的请求元数据呈现，不能覆盖接收方 Bot 信息。接收方任务上下文按来源及请求隔离，同一协作串已确认复用原临时会话自己的最新上下文。

回复默认先回请求 Agent 的邮箱，由它汇总到原聊天。结果离开接收 Agent、进入另一 Bot 的任务或会话前须做输出授权检查；允许执行不自动意味着允许披露全部结果。发送方也不能仅靠重写摘要就绕过数据出口限制。若接收方自身功能需要主动向聊天平台发送消息，该动作使用接收 Bot 身份且目标需要独立授权，不冒用请求者的原回复入口。

接收结果先持久化，再唤醒相应 continuation；等待方释放执行槽，不能占着槽同步等待。设定截止时间、调用深度、请求次数和总预算，限制递归循环。父任务取消默认向仍在工作的子任务发送取消请求，但不等于已撤销外部副作用；终态必须按实际结果记录。迟到结果留审计，不自动重开取消任务。

## 5. 验收与待确认项

验收：伪造 sender/bot_id 不生效；目标 Agent 始终使用自己的 Bot 身份；重试不重复创建任务；无权限通讯被拒绝；同 Bot 不同实例的上下文不串用；跨 Bot 结果出口独立检查；取消、重启和重复回信不破坏任务状态。

待确认：全通的信任范围与执行/结果权限；协作会话回收时长和恢复参数；相关策略的配置形式。
