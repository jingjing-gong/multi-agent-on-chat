# Bot 扫码接入设计

状态：已确认提供 `mac bot add lark` 和 `mac bot add wechat` 扫码加 Bot。本文细化建议流程，仍处于架构设计阶段，未实现命令，也未创建或登录任何 Bot。

## 命令与职责

```text
mac bot add lark [--name <name>]
mac bot add wechat [--name <name>]
```

CLI 发起接入，由各渠道的 onboarding adapter 获取二维码、等待平台确认、校验身份及能力，再交给 Bot Registry 注册。扫码和凭据管理属于 Bot 层，不经过 Agent 推理或写入 Agent conversation context。保留 `mac bot add --config <file>` 作为已有应用的配置接入方式。

## 共同流程

1. 建立独立接入记录，检查名称冲突，显示二维码和有效期。二维码刷新沿用同一接入记录。
2. 等待扫码和平台授权；取消、过期、拒绝均给出可重试状态。
3. 从平台校验结果取得渠道账号或应用的稳定标识，校验必要能力；用户输入的名称仅作显示名。
4. 凭据写入 Bot 专属受限存储，Registry 只持有引用；按渠道及账号/应用标识检查重复注册。重复扫码不创建第二个 Bot，也不静默覆盖旧凭据。
5. 注册成功后连接渠道，分别报告“已注册”“连接中”“就绪”或“需要补充平台配置”。缺少权限时列出具体缺项，不能将扫码成功等同于已经能够收发消息。

建议状态：`pending_scan → verifying → registered → connecting → ready`；另有 `expired`、`cancelled`、`failed` 和 `needs_configuration`。注册前失败清理临时本地材料；注册后连接失败保留 Bot 记录便于恢复。平台上已经创建的应用是否撤销需单独处理，不能声称本地回滚已删除远端应用。

## 渠道差异和身份

| 渠道 | 扫码用途 | 接入校验 |
| --- | --- | --- |
| Lark/飞书 | 通过平台支持的授权流程创建或接入应用 Bot | 应用及 Bot 身份、租户/品牌、必要权限与事件接收配置；创建、发布和权限限制以平台返回结果为准 |
| WeChat | 通过支持的渠道协议登录账号并绑定本地 Bot | 平台返回的账号标识与凭据有效性、消息接收连接；不以用户扫码这一动作推断协议不提供的能力 |

Bot 的执行身份来自经校验的平台凭据。操作 CLI 的本地管理员身份、扫码的人和平台 Bot 身份分别记录。只有平台提供并验证了人类身份及其与本次应用的关联时，才可按身份策略建立用户映射；否则保持未绑定状态。Lark 的 Open ID 按应用隔离，不跨 Bot 复制。扫码不授予 Agent 跨 Bot 的新权限。

Bot 注册与 Agent 创建分开。接入结果可以引导用户用现有模板创建所属 Agent，但是否自动创建默认 Agent 尚待确认；默认不暗中创建。Agent 通过 Bot 能力接口按需获取渠道信息，不接触原始凭据。

## 参考与待定项

参考 codex-on-wechat 的 `src/lark_onboarding.py`（分阶段接入、身份核验、回滚）、`src/lark_cli.py`（终端接入）及 `src/codex_wechat_bot.py` 的二维码获取与状态轮询流程。复用设计，不直接复制旧项目的身份模型或运行数据库。

建议终端同时提供二维码与临时图片路径；具体默认超时、图片保留时间和无终端交互方式在实现设计中确定。是否扫码后自动创建默认 Agent、在线 Gateway 如何接收新增 Bot、平台授权依赖版本仍需细化。
