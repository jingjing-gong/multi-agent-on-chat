# 模板最小字段与当前配置边界

最新用户选择：个人使用；首个引擎 Codex；最多 20 个 Worker；普通消息指导当前工作；配置更新后切换，有上下文则 postpend。群聊/话题粒度未选择（回复为“-”），部署操作系统未指定。本文只设计，不实现。

## 1. 模板最小字段建议

| 字段 | 用途 | 必需性 |
| --- | --- | --- |
| id | 模板唯一标识，用于创建实例 | 必填 |
| version | 不可变模板修订，便于追溯和复现 | 必填，可由注册工具生成 |
| description | 在 /template list 中解释适用任务 | 建议填写 |
| system_prompt | Agent 的角色、任务方式与行为说明 | 核心字段 |
| profile | Codex 配置 profile 引用 | 可选，未指定使用明确的默认配置 |
| model | 模型覆盖 | 可选，省略时从 profile/基础配置解析 |
| effort | 推理强度覆盖 | 可选，省略时继承；显式 default 的语义需区分于省略 |
| skills | 模板希望启用的技能引用 | 可选，第一版不要求每个模板填写 |
| tools | 允许暴露的工具/MCP 能力选择 | 可选；profile 已涵盖时不重复，不能扩大 Bot/运行时权限 |

schema_version 描述模板文件格式，与内容 version 分开。name 显示名可选，省略时使用 id；不是又一项必须填写的业务配置。引擎首版固定 Codex，不要求每个模板重复填写 engine。旧模板例子中的 role 对应 system_prompt，候选字段以本表为新讨论基线。

技能可以包含任务说明或可执行资源，不必假设所有技能都是可强制禁止的工具。skills/tools 筛选的实际隔离方式取决于引擎适配与工具网关，不能只通过提示词声称已限制访问。

## 2. 优先级与快照（建议）

配置解析顺序：基础 Codex 配置 → 指定 profile → 模板显式字段 → 允许的实例覆盖。运行时权限是上界检查，不在这个覆盖链中被放大；凭据使用引用，不存到模板。最终配置、profile 来源及解析摘要随 config_revision 保存，避免可变的 profile 文件让固定版本静默漂移。

profile 不等于 system_prompt 或 AgentTemplate。对项目工作区可能带来的额外配置/AGENTS 指令，执行前必须识别有效来源并定义适用边界；冻结配置不代表冻结外部项目文件。具体 Codex 原生覆盖行为需以选定接入方式核实，上述顺序是新系统希望实现的解析契约。

独立 system_prompt 作为可更新的角色说明。profile 中如果也定义角色/指令，应在解析时明确组合或拒绝冲突，不依赖隐藏默认优先级。同理仅覆盖 model 时必须重新验证继承的 effort 是否兼容。

## 3. 不放进模板的东西

Bot 归属、实例名、真实工作目录放在实例配置；平台身份/凭据由 Bot 和凭据服务管理；用户和协作历史由 Session 管理；20 Worker 全局限额、TTL、任务重试、cron 时间规则和通知投递策略属于平台或任务配置。

旧模板草案中的 functions、required_context、overridable_fields、capability_requirements 暂不强制用户逐项填写。可先由已注册技能/工具的元数据声明需求，由平台解析；有具体功能差异时再暴露高级模板字段。

## 4. 更新与 postpend

按本轮问题范围，用户选择首先用于主用户会话：配置修改提交后立即更新实例的有效版本，不等待 /clear。有上下文时，将新角色说明作为有版本标记的更新信息追加到会话尾部，保留历史。postpend 的拼写沿用用户表述，解释为追加而不是重建整个上下文。

追加说明只用于可表达的指令变化；model、effort、profile 的引擎参数必须通过真实接口切换，不能只发送“已切换模型”的文字。已发出的模型请求和已执行工具不能追溯改写。运行中参数变化在最早支持的调用边界应用，状态展示 applied/pending，不能把持久化成功伪装为引擎已切换。

追加普通文本不等于修改引擎系统层指令。需要核实 Codex 接入方式支持的指令层级与更新接口；若旧指令仍具有更高优先级，必须处理冲突，不能承诺单纯 append 就必然覆盖。建议将可信配置更新与用户原文分开标注，避免用户内容冒充系统配置事件。

前面已确认的协作会话固定创建版本、CronJob 固定版本继续保留；本轮不自动推翻这两个约定。若用户希望更新也覆盖在途协作或旧 Job，应另行明确。动态编辑入口与配置优先级实现仍须选定引擎接口后核验。

## 5. 20 Worker 与个人全通

最多 20 Worker 是用户确认的上限。建议定义为整个部署同时占用的执行 Worker 总数，合计用户、协作与 cron，不是每个 Agent 20 个。等待依赖的会话释放执行槽，队列和持久化 Session 不计为活动 Worker；Worker 内部若启动子执行器也不得绕过总执行预算。物理进程和槽位的精确对应待定。

个人使用使全通可收敛为同一部署内本人管理的 Bot/Agent 默认可发现和通讯。此范围为结合用户选择的建议，不代表外部聊天用户自动取得部署管理权或全部历史可见性。暂不设计跨用户多租户通讯管理。
